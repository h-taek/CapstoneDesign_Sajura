## 1. 외부 데이터 수집 — 미정 소스

> 확정된 입력 데이터는 `docs/spec/08_ai/ml_pipeline.md` 섹션 4 참조.

| 데이터 | 출처 후보 | 상태 |
|---|---|---|
| 경제지표 데이터 | 한국은행 ECOS API / KOSIS | 🟡 |
| 검색량 데이터 | Naver DataLab / Google Trends API | 🟡 |
| SNS 노출도 데이터 | (미정) | 🟡 |

### 1.1 조사가 필요한 항목

- 각 API의 가용성·라이선스·rate limit
- 매장 단위 예측에 실제로 기여하는 신호인지(상관 분석 필요)
- 수집 주기와 n8n 노드 구성 가능성
- MVP 포함 여부 — 효과 검증되지 않으면 2단계로 미룸

---

## 2. 슬라이딩 윈도우 N — 미정

> 현재 spec: "최근 N개월 데이터만 사용".

조사 필요:
- 매장 운영 특성상 의미 있는 학습 구간(3·6·12개월) 비교
- 계절성 반영을 위한 최소 윈도우 길이
- 점주 메뉴 변경·매장 리뉴얼 등 도메인 변화 대응 방식

---

## 3. 결측·이상치 처리 기준 — 상세 정의 필요

> 현재 spec: "IQR 및 Z-score 기반 이상치 탐지" (방법론만 명시).

상세 결정 필요:
- IQR vs Z-score를 어떤 조건에서 선택할지
- 결측 보간 방법 (전일 평균·이동평균·0 채움)
- 이상치 임계 계수(IQR 1.5 / Z 3.0 등)
- 이상 데이터를 "분리"할지 "수정"할지

---

## 4. 알림 전달 방식 — 미정

> 현재 spec: "알림(점주에게 푸시 발송)" → HANDOFF에서 "앱 내 알림으로 정정" 지시.

확정 필요:
- 푸시 알림 미사용 결정의 정책 근거
- 앱 내 알림 채널과 표시 방식(배지·홈 알림 카드 등)

---

## 5. 운영 모니터링 — 미정

> 현재 spec: "n8n 실행 결과 모니터링 대시보드 제공" → HANDOFF에서 "`pipeline_jobs` 테이블 상태 + Slack 알림으로 정정" 지시.

확정 필요:
- `pipeline_jobs` 테이블에서 모니터링할 상태값
- Slack 알림 트리거 조건(실패·지연·정상 종료)
- 운영팀 가시화 화면 필요성

---

## 6. 모델 성능·배포 승인 기준 — 미정

조사 필요:
- 재학습 후 성능 개선 기준값(MAPE 개선 폭)
- 자동 배포 vs 수동 검토 후 배포
- 롤백 절차

---

## 7. POS API 수집 주기·인증 방식 — 미정

조사 필요:
- TossPlace/키움/OKPOS 각각의 API 자격증명 형식
