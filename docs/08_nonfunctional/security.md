# 보안 설계서

## 1. 보안 원칙

- 동의 기반 최소 데이터 수집을 적용한다.
- AI는 추천하고, 결정과 실행은 사용자가 한다.
- 자동 발주와 자동 결제를 분리한다.
- 매출 데이터와 결제 정보는 민감 정보로 보호한다.

## 2. 인증

### 2.1 Google 인증

- Firebase Auth를 사용한다.
- Frontend에서 Google 인증을 수행한다.
- 인증 토큰을 Backend에 전달한다.

### 2.2 카카오 인증

- Authlib를 사용한다.
- OAuth 2.0 흐름은 Backend에서 직접 처리한다.

## 3. 개인정보 및 데이터 보호

- 회원가입 시 수집 항목, 이용 목적, 보유 기간을 명시한다.
- 필수 항목과 선택 항목을 분리해 동의를 받는다.
- 모델 학습에 필요한 최소 데이터만 수집한다.
- 불필요한 정보는 수집 단계에서 차단한다.
- 매장 식별자는 모델 학습 시 해시 처리한다.
- 학습용 데이터는 집계화하여 활용한다.
- 원본 매출 데이터는 점주 본인 계정으로만 접근 가능해야 한다.
- 운영진과 개발자는 별도 권한 절차 없이는 원본 매출 데이터를 조회할 수 없어야 한다.

## 4. 암호화

- 저장 단계에서 AES-256 암호화를 적용한다.
- 백업 데이터도 동일 정책을 적용한다.
- 전송 구간에는 TLS 1.3을 적용한다.

## 5. 접근 통제 및 감사

- RBAC 기반 접근 권한 분리를 적용한다.
- 모든 데이터 접근에 대해 감사 로그를 기록한다.
- 추천 내용, 점주 승인, 수정 이력은 OrderApprovalLog에 기록한다.

## 6. 결제 및 외부 거래

- 카드 원본 정보는 자체 서버를 거치지 않는다.
- PG사 토큰화 방식으로 결제 정보를 처리한다.
- 자체 서버에는 토큰값만 저장한다.
- 실제 결제는 외부 사이트에서 진행된다.
- 일정 금액 이상의 발주는 추가 인증 요구가 필요하다고 기술 문서에 제시되어 있다.

## 7. 외부 API 및 약관

- 외부 인터페이스는 REST API, JSON, OAuth 2.0 표준을 채택한다.
- POS 사업자의 공식 OAuth 2.0 기반 API만 사용해야 한다.
- 승인된 scope 이내로만 데이터를 요청해야 한다.
- API 호출 throttling을 적용해야 한다.
- 외부 라이브러리는 라이선스를 검토해야 한다.

## 8. 사용자 권리

- 마이페이지에서 내 데이터 다운로드 기능을 제공한다.
- CSV 또는 JSON 형식으로 본인 매출/발주 데이터를 추출할 수 있어야 한다.
- 전체 데이터 삭제 요청 기능을 제공한다.
- 회원 탈퇴 시 30일 유예 기간 후 백업 포함 완전 파기한다.
- 파기 완료 시 이메일로 증빙을 발송한다.

## 추가 작업 필요 항목

- 실제 개인정보 수집 항목 목록 정의 필요
- RBAC 역할과 권한 매트릭스 정의 필요
- 감사 로그 필드 정의 필요
- OrderApprovalLog 스키마 정의 필요
- AES-256 적용 대상 컬럼 정의 필요
- 토큰 저장/만료/폐기 정책 정의 필요
- 외부 API별 scope 및 rate limit 정의 필요
