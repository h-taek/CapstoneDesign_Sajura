# 기능 상세 설계서

## 1. 인증 및 회원가입

### 1.1 Google 로그인

- Firebase Auth를 사용한다.
- Frontend에서 Google 인증을 수행한다.
- 인증 토큰을 Backend로 전달한다.
- Backend는 회원 존재 여부를 DB에서 조회한다.
- 신규 사용자이면 회원 정보를 저장한다.

| 구분 | 항목 |
|---|---|
| 입력 | Firebase ID Token |
| 출력 | JWT Access Token, JWT Refresh Token, user_id, email, onboarding_completed |

### 1.2 카카오 로그인

- Authlib를 사용한다.
- OAuth 2.0 흐름은 Backend에서 직접 처리한다.

| 구분 | 항목 |
|---|---|
| 입력 | 카카오 Authorization Code |
| 출력 | JWT Access Token, JWT Refresh Token, user_id, email, onboarding_completed |

### 1.3 JWT 토큰 정책

- Google과 카카오 모두 Backend가 자체 JWT를 발급하여 인증 제공자와 무관하게 동일한 토큰 구조를 사용한다.
- Access Token 유효 기간은 1시간이다.
- Refresh Token 유효 기간은 30일이며 HttpOnly Cookie에 저장한다.
- Refresh Token은 사용 시마다 새 토큰으로 교체한다(Rotation).
- Access Token은 메모리에 저장하며 LocalStorage 저장을 금지한다.

### 1.4 회원가입 초기 설정

온보딩 흐름은 아래 단계를 순서대로 진행한다.

```
1. OAuth 계정 생성 (Google / 카카오)
2. 사업자등록번호 입력 → 국세청 API 즉시 검증
     ├─ 계속사업자 확인 → 다음 단계 진행 허용
     └─ 휴업 / 폐업 / 미등록 → 진행 불가, 오류 메시지 표시
3. 매장 정보 입력 (매장명, 업종, 연락처, 주소)
4. POS 연동 시도
     ├─ 성공 → 전체 기능 활성화
     └─ 실패 → CSV 임시 모드 진행
               ├─ 사용 가능: 메뉴/재고 등록, 기본 판매 데이터 조회
               └─ 비활성화: 수요예측, 자동발주 추천
               + "POS 연동 미완료" 배지 상시 표시
               + 설정 화면에서 언제든 POS 연동 재시도 가능
5. 초기 재고 / 초기 메뉴 입력
6. 메인 화면 진입
```

- 초기 설정 미완료 상태에서 재접속 시 onboarding_completed: false를 로그인 응답에 포함하여 Frontend가 초기 설정 화면으로 강제 이동한다.

| 구분 | 항목 | 비고 |
|---|---|---|
| 입력 | 사업자등록번호 | 필수, 국세청 API 검증 |
| | 매장명 | 필수 |
| | 업종 | 필수 |
| | 연락처 | 필수 |
| | 주소 | 필수 (AI 예측 지역 변수 활용) |
| | 매장 규모 구간 | 필수, 선택지 제공 (소형 ~10석 / 중형 11~30석 / 대형 31석~) |
| | 운영 형태 | 필수, 선택지 제공 (홀 운영 / 배달 전용 / 홀+배달 병행) |
| | POS 종류 및 자격증명 | 필수 시도, 실패 시 CSV 임시 모드 허용 |
| 출력 | store_id | |
| | onboarding_completed | boolean |
| | pos_linked | boolean |
| | pos_mode | "api" / "csv" / "none" |

## 2. 메뉴 관리

### 2.1 메뉴 조회

- 점주가 등록한 메뉴 목록을 조회한다.

| 구분 | 항목 |
|---|---|
| 입력 | store_id |
| 출력 | 메뉴 목록 (menu_id, 메뉴명, 가격, 재고차감_사용 여부, 레시피 존재 여부) |

### 2.2 메뉴 등록

- Backend Service 계층에서 메뉴명 중복을 검증한다.
- 중복이 없으면 메뉴를 저장한다.
- 재고 차감 ON이고 레시피 미입력 시 경고를 반환한다.
- 레시피 입력이 있으면 레시피를 저장한다.

| 구분 | 항목 | 비고 |
|---|---|---|
| 입력 | 메뉴명 | 필수, 중복 불가 |
| | 가격 | 필수 |
| | 재고 차감 사용 여부 | 필수, 기본값 ON |
| | 레시피 (재료명 + 사용량 + 단위) | 재고 차감 ON 시 권장, OFF 시 불필요 |
| 출력 | menu_id | |
| | 저장 완료 여부 | |
| | 경고 메시지 | 재고 차감 ON + 레시피 미입력 시 반환 |

### 2.3 메뉴 수정

- 기존 메뉴를 조회한다.
- 수정 요청 내용을 반영한다.
- 레시피 수정이 있으면 레시피도 수정한다.

| 구분 | 항목 |
|---|---|
| 입력 | menu_id, 수정할 항목 (메뉴명 / 가격 / 재고 차감 사용 여부 / 레시피) |
| 출력 | 수정 완료 여부 |

### 2.4 메뉴 삭제

- 점주 UI에서는 즉시 삭제로 표시되나 DB에는 소프트 삭제로 처리한다.
- `deleted_at` 기준 6개월 후 배치 작업으로 DB에서 영구 삭제한다.
- 삭제된 메뉴의 과거 판매 데이터는 `menu_id` 참조로 유지한다.

| 구분 | 항목 | 비고 |
|---|---|---|
| 입력 | menu_id | |
| 출력 | 삭제 완료 여부 | |
| DB 처리 | is_deleted: true, deleted_at 기록 | 소프트 삭제 |
| 영구 삭제 | deleted_at + 6개월 후 배치 실행 | |

## 3. 재고 관리

### 3.1 초기 재고 등록

- 사용자가 초기 재고를 1회 입력한다.
- 재고관리와 재고품목으로 저장한다.
- 단위는 선택지로 제공한다 (kg / g / L / ml / 개).

| 구분 | 항목 | 비고 |
|---|---|---|
| 입력 | 재료명 | 필수 |
| | 현재 수량 | 필수 |
| | 단위 | 필수, 선택지 제공 (kg / g / L / ml / 개) |
| | 소비기한 | 선택 |
| 출력 | 등록된 재고 항목 수 | |
| | 저장 완료 여부 | |

### 3.2 재고 조회

| 구분 | 항목 |
|---|---|
| 입력 | store_id |
| 출력 | 재고 목록 (item_id, 재료명, 현재 수량, 단위, 소비기한, 재고 확인 필요 여부, 최종 업데이트 일시) |

### 3.3 자동 재고 차감

- POS 판매 데이터가 저장된다.
- 판매 메뉴를 레시피와 매핑한다.
- 레시피 필요수량을 기반으로 재고품목 현재수량을 차감한다.
- 재고 차감 시 수량이 0 미만으로 내려가지 않도록 0에서 멈춘다.
- 재고 부족 발생 시 해당 재료를 "재고 확인 필요" 상태로 표시하고 점주에게 알림을 발송한다.
- 홈/대시보드에 경고 배지를 상시 노출하며 점주가 수동 재고 업데이트 완료 시 상태를 해소한다.

| 구분 | 항목 | 비고 |
|---|---|---|
| 입력 | 판매된 메뉴 목록 + 수량 (POS 데이터) | |
| 출력 | 차감 완료 여부 | |
| | 차감 후 재고 수량 | |
| | 재고 부족 재료 목록 | 부족 발생 시 반환, 알림 트리거 |

### 3.4 재고 수정

- 기존 재고를 조회한다.
- 수정 요청 내용을 반영한다.
- 수정 이력을 기록한다.

| 구분 | 항목 | 비고 |
|---|---|---|
| 입력 | item_id | |
| | 수정 수량 또는 소비기한 | |
| | 수정 사유 | 필수, 선택지 제공 (실사 조정 / 납품 입고 / 기타) |
| 출력 | 수정 완료 여부 | |
| 이력 기록 | 수정 전 수량, 수정 후 수량, 수정 사유, 수정 일시, user_id | |

### 3.5 재고 폐기

- 폐기 요청을 수신한다.
- 서버는 현재 재고 수량을 조회한다.
- 폐기 가능 수량이 충분하면 재고를 차감한다.
- 재고가 부족하거나 조건이 불충분하면 오류를 반환한다.

| 구분 | 항목 | 비고 |
|---|---|---|
| 입력 | item_id, 폐기 수량 | |
| 출력 | 폐기 완료 여부 | |
| | 차감 후 재고 수량 | |
| 오류 | 현재 수량 부족 시 오류 반환 | |

### 3.6 소비기한 관리

- 식자재 소비기한을 자동 관리하고 알림을 제공한다.
- 구체적 구현 방식은 추후 정의한다.

## 4. POS 연동

### 4.1 지원 방식

- CSV 업로드 (POS API 연동 실패 시 임시 대안)
- POS API 연동

### 4.2 어댑터 구조

| POS 소스 | 어댑터 | 공통 스키마 |
|---|---|---|
| 토스플레이스 | TossPlaceAdapter | `{ "timestamp": ..., "item_id": ..., "qty": ..., "unit": "kg" }` |
| 키움페이 | KiwoomAdapter | 동일 공통 스키마 |
| OKPOS | OKPOSAdapter | 동일 공통 스키마 |
| CSV / Excel 업로드 | CSVAdapter | 동일 공통 스키마 |

### 4.3 POS API 연동

- POS사별 API 자격증명 형식은 추후 각 POS사 API 문서 확인 후 정의한다.

| 구분 | 항목 | 비고 |
|---|---|---|
| 입력 | POS 종류 선택 | TossPlace / 키움페이 / OKPOS |
| | API 자격증명 | POS사별 형식 추후 정의 |
| | store_id | |
| 출력 | 연동 성공/실패 여부 | |
| | 초기 데이터 수집 건수 | |

### 4.4 CSV 업로드

- 사주라가 제공하는 고정 템플릿 형식만 허용한다.
- 템플릿 다운로드 링크를 업로드 화면에서 제공한다.

| 구분 | 항목 | 비고 |
|---|---|---|
| 입력 | CSV / Excel 파일 (고정 템플릿 형식) | |
| | store_id | |
| 출력 | 파싱 성공 건수 | |
| | 이상치 탐지 건수 및 비율 | |
| | 저장 완료 여부 | |

### 4.5 공통 스키마 변환 (어댑터)

| 구분 | 항목 |
|---|---|
| 입력 | POS 원본 데이터 (각 POS별 포맷) |
| 출력 | `{ timestamp, item_id, qty, unit }` 공통 스키마로 변환된 데이터 |

### 4.6 데이터 품질 처리

- JSON Schema 또는 Pydantic으로 스키마를 검증한다.
- IQR 및 Z-score 기반으로 이상치를 탐지한다.
- 이상치 비율에 따라 처리 방식을 분기한다.

| 이상치 비율 | 처리 방식 |
|---|---|
| 5% 미만 | 이상 데이터를 학습 데이터에서 자동 분리 후 진행 (알림 없음) |
| 5% 이상 | 점주에게 알림 발송 → 복구 또는 폐기 선택 요청 |

| 구분 | 항목 | 비고 |
|---|---|---|
| 입력 | 공통 스키마 변환된 데이터 | |
| 출력 | 정상 데이터 | 학습 데이터셋 편입 |
| | 이상치 데이터 | 분리 저장 |
| | 이상치 비율 | 5% 이상 시 점주 알림 트리거 |

## 5. 수요예측

### 5.1 배치 예측 (야간 자동 실행)

- n8n이 매일 02:00에 전체 매장의 메뉴별 예측을 수행한다.
- 예측 대상은 재고 차감 여부와 무관하게 전체 메뉴이다.
- 예측 결과는 DB에 사전 저장하여 점주 요청 시 즉시 반환한다.

| 구분 | 항목 |
|---|---|
| 입력 | 과거 판매 데이터, 날씨, 요일/공휴일, 유동인구, 검색량, SNS 노출도, 주변 행사 정보, 레시피 |
| 출력 | 메뉴별 1~3일 예상 수요, SHAP 기반 예측 근거, 예측 신뢰도 점수 |

### 5.2 예측 결과 조회 (점주 요청)

- DB 캐시를 우선 조회하여 반환한다.
- 저장된 예측 결과가 없을 경우 AI Server를 직접 호출하고 결과를 DB에 저장한다.

| 구분 | 항목 | 비고 |
|---|---|---|
| 입력 | store_id, menu_id (선택) | |
| 출력 | 메뉴별 1~3일 예상 수요 | |
| | Top-3 영향 변수 자연어 설명 | |
| | 신뢰도 낮음 경고 배지 | 아래 조건 중 하나라도 해당 시 표시 |

### 5.3 신뢰도 경고 기준

아래 조건 중 하나라도 해당하면 "신뢰도 낮음" 경고 배지를 표시한다.

| 조건 | 기준값 |
|---|---|
| MAPE | 20% 초과 |
| 학습 데이터 기간 | 30일 미만 |
| 최근 30일 결측값 비율 | 30% 초과 |

### 5.4 Cold-start 처리

- 신규 매장은 자체 데이터 30일 축적 전까지 유사 매장 기반 예측 결과를 제공한다.
- 유사 매장 기준은 동일 업종, 유사 상권, 매장 규모 구간 및 운영 형태를 모두 적용한다.
- 유사 매장 기반 예측 결과에는 "신뢰도 낮음" 경고 배지를 필수 표시한다.
- 자체 데이터 30일 축적 후 자체 예측으로 자동 전환한다.

### 5.5 예외

- POS 미연동(CSV 임시 모드) 상태에서는 수요예측 기능을 비활성화한다.

## 6. 추천발주

### 6.1 추천발주 생성 (배치)

- 수요예측 배치 완료 후 연속으로 실행한다.
- 추천발주안을 DB에 사전 저장한다.
- 발주 연동 대상은 쿠팡이며 이후 추가 업체 확장을 고려한다.
- 리드타임과 안전재고는 점주가 재료별로 직접 입력한다.

| 구분 | 항목 | 비고 |
|---|---|---|
| 입력 | 수요예측 결과 | 메뉴별 일일 예상 판매량 |
| | 레시피 소모량 | 메뉴→재료 변환 |
| | 현재 재고 | DB 실시간 조회 |
| | 리드타임 | 점주 직접 입력 (일 단위) |
| | 안전재고 | 점주 직접 입력 (재료 단위) |
| 출력 | 품목별 권장 발주 수량 | |
| | 예상 소진 시점 | |
| | 추천 근거 | |

### 6.2 추천발주 산식

**재료별 일일 소모량**
```
일일 소모량 = Σ (메뉴별 일일 예상 판매량 × 레시피 재료 사용량)
```

**권장 발주 수량**
```
발주 필요량 = (일일 소모량 × 리드타임) + 안전재고 - 현재 재고
권장 발주 수량 = max(발주 필요량, 0)  ← 음수이면 발주 불필요
```

**예상 소진 시점**
```
예상 소진 시점 = 오늘 + (현재 재고 / 일일 소모량)
```

**산식 예시 (원두)**

| 항목 | 값 |
|---|---|
| 일일 예상 판매량 (아메리카노) | 50잔 |
| 레시피 원두 사용량 | 15g / 잔 |
| 일일 원두 소모량 | 750g (0.75kg) |
| 리드타임 | 2일 |
| 안전재고 | 1kg |
| 현재 재고 | 2kg |
| 발주 필요량 | (0.75 × 2) + 1 - 2 = **0.5kg** |
| 예상 소진 시점 | 오늘 + (2 / 0.75) = **약 2일 후** |

### 6.3 추천발주 조회 (점주 요청)

|---|---|
| 입력 | store_id |

- 점주가 발주를 확정한다.

## 7. 쿠팡 장바구니 자동 담기

- 점주가 발주를 확정하면 발주 기록을 저장한다.

- Backend가 완료 응답을 반환한다.
