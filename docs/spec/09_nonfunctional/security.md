# 보안 설계서

## 1. 보안 원칙

- 동의 기반 최소 데이터 수집을 적용한다.
- AI는 추천하고, 결정과 실행은 사용자가 한다.
- 자동 발주와 자동 결제를 분리한다.
- 매출 데이터와 결제 정보는 민감 정보로 보호한다.

## 2. 인증

### 2.1 소셜 로그인 (Google / 카카오)

> 인증 흐름 상세: feature_spec.md 섹션 1.1

- Google과 카카오 모두 **Authlib 라이브러리로 Backend에서 OAuth 2.0 흐름을 처리**한다. Firebase SDK 미사용.
- Frontend는 로그인 버튼 클릭 시 Backend의 인가 URL(`GET /api/auth/login/google`, `GET /api/auth/login/kakao`)로 리다이렉트만 수행한다.
- Backend 콜백에서 사용자 정보를 조회하고 자체 JWT를 발급한다.
- 인증 제공자와 무관하게 동일한 자체 JWT 구조를 사용한다.

### 2.2 이메일/비밀번호 로그인

- 비밀번호는 **bcrypt**로 해시하여 저장한다. 원문은 저장하지 않는다.
- 소셜 로그인 계정은 비밀번호 변경 기능을 사용할 수 없다.

### 2.3 토큰 정책

> JWT 유효기간 기준: feature_spec.md 섹션 1.3 / 토큰 DB 스키마: schema.md 3.2

**토큰의 역할**

HTTP는 요청 간 상태를 유지하지 않는다. 토큰은 매 요청마다 "이 요청이 누구의 것인지"를 서버에 증명하는 수단이다.

- Access Token (JWT): 서명 검증만으로 인증 가능 (DB 조회 불필요). `user_id`, `store_id`, 만료 시각을 포함한다.
- Refresh Token: Access Token 갱신 전용. API 요청에 직접 사용하지 않는다.

**Access Token**

| 항목 | 내용 |
|------|------|
| 유효기간 | 1시간 |
| 저장 위치 | Frontend 메모리 (LocalStorage 저장 금지) |
| 만료 시 | 401 반환 → Frontend가 자동으로 Refresh Token 갱신 요청 후 원래 요청 재시도 |

**Refresh Token**

| 항목 | 내용 |
|------|------|
| 유효기간 | 30일 |
| 저장 위치 | HttpOnly Cookie (JavaScript 접근 불가) |
| DB 저장 방식 | 원문 미저장, SHA-256 해시값(`token_hash`)만 저장 — DB 침해 시 원문 복구 불가 |
| Rotation 정책 | 사용마다 새 토큰으로 교체, 기존 토큰 즉시 폐기(`is_revoked: 1`) |
| 만료/폐기 시 | 401 반환 → 로그인 화면 이동 |

**Rotation의 보안 효과**

Rotation은 Refresh Token 자체가 탈취된 경우에 유효하다. 탈취된 토큰이 사용되면 정상 사용자의 다음 갱신 시도에서 충돌이 감지되어 강제 재로그인이 발생한다. 단, 이메일·비밀번호 등 자격증명이 탈취된 경우에는 Rotation만으로 방어할 수 없다 — 이는 별도 계정 보호 수단(비정상 로그인 감지 등)의 영역이다.

**로그아웃**

- Refresh Token을 DB에서 `is_revoked: 1`로 즉시 폐기한다.
- HttpOnly Cookie에서 제거한다.

**다중 디바이스 로그인**

각 디바이스(PC·모바일 등)는 자체 Refresh Token을 발급받아 독립 Rotation 흐름을 유지한다. 한 디바이스의 Rotation·로그아웃은 다른 디바이스에 영향을 주지 않는다 — `refresh_tokens` 테이블의 user_id 동일·token_hash 별도 행으로 구분된다.

**강제 로그아웃 (모든 디바이스)**

분실·도난·계정 도용 의심 시 점주가 `POST /api/auth/logout-all`을 호출하면 해당 user_id의 활성 `refresh_tokens` 전체를 `is_revoked: 1`로 일괄 폐기한다. Access Token은 서명 검증만으로 동작하므로 자체 무효화 불가 — 최대 1시간(Access Token 유효기간) 이내 모든 디바이스가 401 응답을 받고 재로그인으로 이동한다.

## 3. 개인정보 및 데이터 보호

- 회원가입 시 수집 항목, 이용 목적, 보유 기간을 명시한다.
- 필수 항목과 선택 항목을 분리해 동의를 받는다.
- 모델 학습에 필요한 최소 데이터만 수집한다.
- 불필요한 정보는 수집 단계에서 차단한다.
- 매장 식별자는 모델 학습 시 해시 처리한다.
- 학습용 데이터는 집계화하여 활용한다.
- 원본 매출 데이터는 점주 본인 계정으로만 접근 가능해야 한다.
- 운영진과 개발자는 별도 권한 절차 없이는 원본 매출 데이터를 조회할 수 없어야 한다.

### 3.1 개인정보 수집 항목

**필수 수집 항목 (회원가입·온보딩)**

| 항목 | 수집 목적 |
|------|----------|
| 이메일 | 계정 식별, 알림 발송 |
| 사업자등록번호 | 국세청 API 계속사업자 검증 |
| 매장명, 업종, 연락처, 주소 | 매장 운영 및 AI 예측 지역 변수 활용 |
| 매장 규모 구간, 운영 형태 | Cold-start 유사 매장 매칭 기준 |

**서비스 이용 중 수집**

| 항목 | 수집 목적 |
|------|----------|
| POS API 자격증명 | POS 연동 인증 (AES-256-GCM 암호화 저장) |
| 판매 데이터 | 수요예측 모델 학습·추론 입력 |
| 재고 입력 데이터 | 추천발주 산출 기준 |
| 발주 내역, 점주 수정 이력 | 모델 재학습 피드백 |

**미수집 항목**

| 항목 | 이유 |
|------|------|
| 결제 카드 정보 | 쿠팡에서 직접 처리, 자체 서버 미경유 |
| GPS·위치 정보 | 주소 텍스트만 수집, 실시간 위치 미수집 |

**보유 기간**

- 서비스 이용 기간 동안 보유한다.
- 회원 탈퇴 후 30일 유예 기간 경과 시 백업 포함 완전 파기한다.
- 파기 완료 시 이메일로 증빙을 발송한다.

## 4. 암호화

- 백업 데이터에도 동일 암호화 정책을 적용한다.
- 전송 구간에는 TLS 1.3을 적용한다.
- TLS 종료는 외부 엣지(Caddy v2)에서 수행한다. 내부 BE upstream은 HTTP/1.1 평문이며 같은 호스트 또는 컨테이너 네트워크 내부로 한정한다. (구성 상세: `service_design.md` §1, `docs/research/backend/03_reverse_proxy.md` §4)

### 4.1 저장 암호화 적용 대상

> 컬럼별 적용 방식 원본: schema.md 인덱스 설계 요약

암호화 적용 기준: 유출 시 외부 서비스에 직접 피해를 줄 수 있는 자격증명, 또는 원문 복구가 불가능해야 하는 값.

| 컬럼 | 방식 | 이유 |
|------|------|------|
| `pos_connections.api_key` | AES-256-GCM (애플리케이션 레벨) | POS 외부 서비스 접근 자격증명 — 유출 시 타 매장 데이터 접근 가능 |
| `refresh_tokens.token_hash` | SHA-256 해시 | 원문 미저장 — DB 침해 시 토큰 원문 복구 불가 |

**비적용 항목**

| 항목 | 이유 |
|------|------|
| 이메일, 매장명 등 식별 필드 | 검색·조회가 필요한 필드는 암호화 시 인덱스 사용 불가 |
| 판매 데이터, 재고 데이터 | 집계·분석이 빈번하여 암호화 시 성능 저하 |

## 5. 접근 통제 및 감사

### 5.1 레이어 1 — 애플리케이션 접근 통제 (사용자 단)

**현재 적용:**

- 점주 단일 역할 기반으로 운영한다.
- JWT payload에 포함된 `store_id`를 모든 API 요청에서 요청 대상 데이터의 `store_id`와 대조한다.
- 불일치 시 403을 반환하여 다른 매장 데이터 접근을 차단한다.

**추후 확장:**

- 직원·관리자 계정이 추가될 경우 RBAC 기반으로 역할별 권한을 분리한다.

> 기준: requirements.md 섹션 4 보안 요구사항

---

### 5.2 레이어 2 — DB·인프라 접근 통제 (시스템/개발자 단)

**현재 적용됨.**

> DB 계정 권한 상세: schema.md 섹션 5

| 계정 | 용도 | 접근 방식 |
|------|------|----------|
| `app_user` | Backend 애플리케이션 | SELECT, INSERT, UPDATE, DELETE (DDL 없음) |
| `n8n_user` | n8n 배치 워크플로우 | 배치 산출물·실행 이력 테이블에만 쓰기 권한 |
| `dev_readonly` | 개발자 디버깅·조회 | SELECT 전체, **VPN 경유 필수** |
| `ops_readonly` | 운영팀 모니터링 | SELECT 집계 테이블만, **VPN 경유 필수** |

- DB 직접 접근은 VPN 또는 배스천 호스트를 경유한다.
- 개발자·운영팀은 원본 매출 데이터를 별도 권한 절차 없이 조회할 수 없다.
- n8n은 운영 데이터 원본을 삭제하지 않는다. 쓰기 대상은 배치 산출물과 실행 이력 테이블로 제한한다.

### 5.3 감사 로그

> 각 테이블 스키마 상세: schema.md 해당 섹션

| 테이블 | 기록 내용 | 추적 항목 |
|--------|----------|----------|

| `disposal_logs` | 재고 폐기 이력 (품목, 수량, 일시) | `user_id`, `store_id`, `created_at` |
| `inventory_lots` | 재고 입고·수량·소비기한 변경 이력 | 로트별 변경 추적 |
| `pipeline_jobs` | 배치 실행 이력 (시작/종료, 성공/실패) | `triggered_by`, `status`, `created_at` |

**보관·조회·무결성 정책**

| 항목 | 정책 |
|------|------|
| 보관 기간 | 1년 (개인정보보호법 일반 권장 + 디스크 부담 적정) |
| 보관 초과 처리 | 매월 1회 배치로 1년 초과 행 archive(cold storage 이전 또는 삭제) |

| 무결성 | DB append-only(INSERT only) + 정기 백업. 해시 체인 등 추가 무결성 메커니즘은 운영 부담 대비 가치 작아 MVP 미적용 |

## 6. 결제 및 외부 거래

- 카드 원본 정보는 자체 서버를 거치지 않는다.
- PG사 토큰화 방식으로 결제 정보를 처리한다.
- 자체 서버에는 토큰값만 저장한다.
- 실제 결제는 외부 사이트에서 진행된다.
- 일정 금액 이상의 발주는 추가 인증 요구가 필요하다고 기술 문서에 제시되어 있다.

## 7. 외부 API 및 약관

- 외부 인터페이스는 REST API, JSON, OAuth 2.0 표준을 채택한다.
- POS 사업자의 공식 OAuth 2.0 기반 API만 사용해야 한다.
- 승인된 scope 이내로만 데이터를 요청해야 한다.
- API 호출 throttling을 적용해야 한다.
- 외부 라이브러리는 라이선스를 검토해야 한다.

## 8. 사용자 권리

- 마이페이지에서 내 데이터 다운로드 기능을 제공한다.
- CSV 또는 JSON 형식으로 본인 매출/발주 데이터를 추출할 수 있어야 한다.
- 전체 데이터 삭제 요청 기능을 제공한다.
- 회원 탈퇴 시 30일 유예 기간 후 백업 포함 완전 파기한다.
- 파기 완료 시 이메일로 증빙을 발송한다.
